실제 구현·검증 결과는 [EXT-FINAL](../handoff/EXT-FINAL.md), [EXT-01](../handoff/EXT-01.md), [EXT-02](../handoff/EXT-02.md), [EXT-03](../handoff/EXT-03.md), [EXT-04](../handoff/EXT-04.md)를 따른다. 아래 내용은 구현 전 정합성 검토와 지시문의 기록이며 현재 구현 상태를 대신하지 않는다.

## 먼저 준비할 공통 기반

1. PR #8의 최신 리뷰와 변경을 확인한다. 사진 저장·정리(`PhotoStore`, `PhotoRetention`), `LocalPurge`, `purge_generation`, 계정 작업과 `SyncWriter.runOwnedTransaction` 계약을 첫 구현 기반에 반영해야 한다. PR #8을 지금 main에 병합하거나 이미 병합됐다고 간주하지 않는다. 검토된 #8을 통합 브랜치에 포함하거나, 별도로 main에 반영된 경우 그 main을 반영한다. 그 전에는 계약·fixture 작업까지 가능하며 중복 PhotoStore를 만들지 않는다.
2. 기존 `CLAUDE.md`, `docs/decisions.md`, 각 세션 지시문과 최신 인계를 읽는다. 문서 주석보다 실제 실행 경로를 우선 확인한다. 예를 들어 현재 DB 헤더의 로그아웃 wipe 설명과 달리 실제 로그아웃은 DB 기록을 유지한다.
3. 새 API/도메인은 버전 있는 계약과 Fake부터 작성한다. 기존 `ReadingEngine`, `SeatEngine`, 동기화 wire 포맷을 몰래 확장하지 않는다. 변경은 `CONTRACT-CHANGE`, 스키마 변경은 `SCHEMA-CHANGE`로 표시한다.
4. 새 SQL 마이그레이션 번호는 통합 브랜치와 main을 보고 배정한다. PR #8에 `0012_purge_request.sql`, `0013_purge_receipts.sql`이 있으므로 재사용하지 않는다. 적용된 마이그레이션은 수정하지 않는다.
5. OCR/풀이 모델의 실행 장소·모델/가중치 버전·비용 한도·보관 정책을 세션 시작 산출물로 남긴다. 대형 Python/모델 추론은 별도 worker, Supabase Edge는 인증·소유권·작업 조정 경계로 설계한다. 인프라가 없으면 Fake 통합까지의 상태를 명시하고 실제 모델 완료라고 보고하지 않는다.
6. 현재 `lib/core/contracts/providers.dart`의 ReadingEngine과 SyncEngine은 Fake다. 새 OCR/solver provider는 dev Fake와 실제 구현의 선택을 명시하고 운영에서 Fake 결과를 실제 모델 결과로 보이지 않게 한다. 기존 S13 동기화 구현은 별도 선행 작업이다. 신규 데이터의 sync 계약은 준비하되, 실제 앱↔서버 왕복 완료에는 S13의 실제 엔진 연결·검증이 필요하다. 이 준비 문서가 S13을 구현했다고 간주하지 않는다.

## 브랜치와 인계 규칙

- 통합 브랜치는 PR #9 하나를 유지한다. `work/ext-01-ocr` → `work/ext-02-solver` → `work/ext-03-gaze` → `work/ext-04-db-encryption`은 준비 때 제안한 작업 브랜치명이다. 실제로는 하나의 작업 체크아웃에서 순서대로 구현하고 단계별 커밋을 같은 통합 브랜치에 반영했다.
- 각 브랜치는 바로 앞 세션을 검증해 반영한 **통합 브랜치의 최신 HEAD**에서 시작한다. 매번 오래된 main에서 갈라서지 않는다. 완료 후 검토된 커밋만 통합 브랜치에 반영하고 main에는 병합하지 않는다.
- 공용 계약·DB·라우터·부트스트랩은 해당 시점의 세션 한 곳에서만 변경한다. 세션별 main 대상 PR 4개를 만들거나 각각 main에 squash하지 않는다.
- `CLAUDE.md`의 “PR 1개 = 세션 1개”는 이번 사용자의 “세션별 진행 후 일괄 병합” 지시에 따라 예외다. GPT 직접 작업 요청에 따른 역할 예외도 기존 S14처럼 PR에 남긴다. 사용자 요청은 준비·구현을 허용하지만 이번 준비 세션에서 main 병합을 허용한 것은 아니다.
- 각 세션은 `docs/handoff/EXT-0N.md`를 생성한다(현재 EXT-01~04 인계 작성됨). 아래 항목을 남겨 다음 세션이 이전 대화를 몰라도 이어갈 수 있게 한다.

| 필수 인계 항목 | 기록 내용 |
|---|---|
| 기준 | 시작/종료 commit SHA, 반영한 선행 PR, 충돌 해결 내용 |
| 실제 적용 | 라이브러리/파일/패키지/모델 고정 버전, 부분 차용 범위, 라이선스와 배포 고지 |
| 계약 | API/모델/schema 버전, 공용 파일, 결정 문서 변경, 기능 플래그 기본값 |
| 검증 | 실행 명령·환경·결과 링크·fixture 해시, 실측치, 미검증/실패 항목 |
| 다음 세션 | 의존성, 남은 결정, 되돌리기 또는 복구 방법, 원문/키/사진을 제외한 재현 절차 |

## 완료를 구분하는 방법

“준비 완료”, “구현 완료”, “자동 검증 완료”, “모델 평가 완료”, “실기기 검증 완료”, “운영 활성화 가능”을 따로 기록한다. 라이브러리 설치, Fake 통과, CI 통과만으로 네 기능이 완성됐다고 판정하지 않는다. 기능을 끈 채 병합하는 경우도 사용자가 요청한 네 기능 전체 완료와 구분한다.

이 준비 문서 자체는 구현 전 계획의 기록이다. 최신 코드 변경과 검증 상태는 EXT-FINAL을 참고한다. 정확도, 성능 향상, 집중 판독 성공률, 암호화 완료 수치를 아직 주장하지 않는다.
